# Users persistence and service — steps 1–4

Implemented scope: User entity, AccountStatus/SystemRole enums, UserRepository, PostgreSQL migration V1, DTOs and UserService, including internal account-status operations and status-filtered listing. No controller, registration endpoint, authentication, administrator authorization, notifications, permissions or project membership is implemented. Other domains call UserService directly through Java, never UserRepository.

## Files and mapping

`users/entity/User.java` describes a database row. The enums define stored role and status names. `users/repository/UserRepository.java` provides database access, and `db/migration/V1__create_users.sql` creates the table. All Java paths are under `backend/src/main/java/com/eclectics/worksync/`; the migration is under `backend/src/main/resources/`.

| Java field | PostgreSQL users column | Type / rule |
| --- | --- | --- |
| id | id | UUID primary key; generated by JPA, or PostgreSQL for direct inserts |
| firstName | first_name | VARCHAR(80), NOT NULL |
| lastName | last_name | VARCHAR(80), NOT NULL |
| email | email | VARCHAR(254), NOT NULL; unique lower(email) index |
| phoneNumber | phone_number | VARCHAR(16), NOT NULL; E.164 string |
| passwordHash | password_hash | VARCHAR(512), NOT NULL; encoded value only |
| role | role | VARCHAR(16), NOT NULL; USER / ADMIN; default USER |
| status | status | VARCHAR(32), NOT NULL; default PENDING_APPROVAL |
| createdAt | created_at | TIMESTAMP WITH TIME ZONE, NOT NULL |
| updatedAt | updated_at | TIMESTAMP WITH TIME ZONE, NOT NULL |

Roles and statuses use names rather than enum ordinal numbers. SQL checks restrict their allowed values. Timestamps are Java Instant values; JPA lifecycle callbacks initialize both and refresh updatedAt on entity updates. Direct SQL inserts receive timestamp defaults, but direct SQL updates must explicitly maintain updated_at; no database update trigger is installed.

No migrations existed, so V1 is the first version. Flyway creates the schema; the existing `spring.jpa.hibernate.ddl-auto=validate` remains unchanged. Do not edit V1 after applying it to a shared database: add a new migration instead.

## Contract for Auth

- Auth owns raw passwords, password encoding, verification, JWTs, login and password reset. The Users constructor accepts an **already-encoded** passwordHash, with room for encoder identifiers and future hash formats. Users does not hash or verify it; callers must not pass a raw password. Hash length is separate from the OpenAPI raw-password length limit.
- New User instances always start as USER / PENDING_APPROVAL. Registration cannot supply a role or status. Account status changes only through the controlled entity methods described below; no general setStatus or role-change method exists.
- Email is trimmed and lowercased using Locale.ROOT in the constructor and before JPA writes. Do not lowercase passwords. Auth submits account details through CreateUserCommand to UserService.createPendingUser; the service normalizes email before validating the command and preserves this normalization contract. Repository findByEmail/existsByEmail also trim and compare case-insensitively, so callers need not normalize lookup input themselves.
- PostgreSQL's unique lower(email) index is the final uniqueness guarantee, including concurrent inserts and mixed-case direct SQL writes. existsByEmail is only a convenience pre-check and cannot prevent races. Direct SQL writers must trim email (enforced by a check) and should lowercase it too. No email provider-specific rewriting, such as removing dots or plus suffixes, is performed. Internationalized-email support needs an explicitly agreed Unicode/collation policy before expanding the contract beyond ordinary email addresses.
- phoneNumber is a string matching E.164, including the leading plus; this layer rejects local formats rather than guessing a country. Names, email, phone and hash have persistence validation constraints. Auth remains responsible for request validation and raw-password policy.
- passwordHash is private, has no public setter, and its trusted-backend getter is annotated JsonIgnore. Do not log it, include it in DTOs, or return User entities from HTTP endpoints. This annotation is defense in depth, not permission to serialize entities.
- UserRepository belongs to Users. Auth can call UserService.createPendingUser with an already-encoded hash. getUserById and getUserByEmail return safe UserResponse records only; there is no credential lookup interface yet. Design any trusted authentication-details lookup separately in a later step.

## Differences from the draft OpenAPI

The account status and system role values match `docs/openapi.yaml`. Names, email and phone lengths/formats follow its registration schema. The request's password is an Auth input; only its encoded hash is persisted here.

The draft uses opaque string IDs with examples such as usr_101, while this task explicitly requires UUID persistence. UUIDs can be represented as strings, but the team must agree future API representation and update examples/format before implementing HTTP DTOs. The draft UserRecord also requires a permissions array; permission persistence is outside this task and is not added. Do not expose this entity as UserRecord. updatedAt is mandatory in persistence even though the draft makes it optional in responses. The supplied API draft remains unchanged.

## Tests and running them

`backend/src/test/java/com/eclectics/worksync/users/repository/UserRepositoryTests.java` reuses the existing SpringBootTest / test profile and real PostgreSQL. Tests cover round-trip persistence, Java and SQL defaults, normalization and lookups, duplicate emails through JPA and direct SQL, status pagination, and update timestamps. Each test runs in a rolled-back transaction. No Testcontainers, H2 or additional dependencies are added.

Follow the README to create a separate disposable PostgreSQL database and export TEST_DB_URL, TEST_DB_USER and TEST_DB_PASSWORD. Then run from the repository root:

```sh
(cd backend && ./mvnw verify)
# Or run just the repository integration tests:
(cd backend && ./mvnw -Dtest=UserRepositoryTests test)
```

Flyway applies V1 before Hibernate validates the mapping. Do not point tests at production or a shared development database. A passing Maven validate goal only checks project configuration; it does not compile code or run these tests.

## Basic UserService — step 3

`users/service/UserService.java` is a concrete Spring service injected with UserRepository and Jakarta Validator. Explicit validation uses the existing DTO constraints without relying on future HTTP @Valid annotations. Email is trimmed and lowercased with Locale.ROOT before creation validation and lookup; blank, missing or malformed email fails validation. Null command/request/UUID arguments are rejected as internal programming errors. Creation never encodes or changes the supplied hash and relies on the entity's USER / PENDING_APPROVAL defaults.

Methods:

- createPendingUser(CreateUserCommand): validate, check email, save and return UserResponse.
- getUserById(UUID): return a safe response or throw UserNotFoundException.
- getUserByEmail(String): safe internal lookup only, not an unrestricted public email endpoint or credential lookup.
- updateProfile(UUID, UpdateProfileRequest): validate and update only firstName, lastName and phoneNumber. ID, email, hash, role, status and createdAt are preserved.

The class has read-only transactions by default; create/update override with write transactions. saveAndFlush forces persistence validation and lifecycle callbacks before constructing the response, including updatedAt. Runtime failures propagate for rollback. Auth must call the Spring-managed service bean; a manually constructed service has no Spring transaction interception. If Auth starts an outer transaction, Users joins it and database failures must propagate until that transaction rolls back too. No authorization policy is implemented here: future trusted callers/controllers must enforce current-user/admin access before selecting a user ID.

### Duplicate-email and error boundary

The friendly existsByEmail pre-check throws DuplicateEmailException with a fixed, safe message. It cannot eliminate concurrent registration races. The existing PostgreSQL unique index ux_users_email_lower is authoritative.

UserService deliberately does not catch or retry DataIntegrityViolationException inside a failed transaction. For a database race, that unchecked exception leaves the service and triggers rollback. A future API boundary handler, **outside the outermost transaction**, should distinguish the wrapped Hibernate constraint metadata: SQLSTATE 23505 and constraint name ux_users_email_lower. Map only that known email conflict (and DuplicateEmailException) to the documented safe 409 error, using a fixed code/message. Do not parse raw SQL messages or label every integrity violation as duplicate email. Other constraint failures must remain distinct. UserNotFoundException can later map to a safe 404. No HTTP handler or status mapping is added in this step.

Do not log commands, password hashes, raw database exceptions or constraint violation rejected values. Construct validation error DTOs from safe field names/messages only; never serialize exception objects or getInvalidValue().

### Service tests

UserServiceTests adds 12 unit tests using Mockito and a real Jakarta Validator, without PostgreSQL. These cover creation/defaults/hash preservation, duplicate pre-checks, propagation of persistence failures, ID/email lookup, missing users, allowed profile changes, protected-field preservation and invalid input. UserServiceIntegrationTests adds two tests using the existing PostgreSQL test profile and rolled-back transactions, verifying real service persistence, duplicate detection and flushed update timestamps. Unit tests do not verify transaction rollback or database uniqueness; the PostgreSQL suite is needed for database behavior.

## Internal administrator account operations — step 4

These methods are **internal Java operations for future authorized administrator workflows**, not secured APIs. A method name such as approveUser is not an authorization rule. Before integrating a secured AdminUserController, the Auth/Security owner must enforce ADMIN and effective account status on every administration route, including listing. Ordinary-user profile endpoints must never call these status methods or accept status/role fields. Future trusted Java callers need the same authorization boundary. No public endpoint, JWT/security configuration or role promotion is introduced here.

| Entity method | Required current status | New status | Service method |
| --- | --- | --- | --- |
| approve() | PENDING_APPROVAL | ACTIVE | approveUser(UUID) |
| reject() | PENDING_APPROVAL | REJECTED | rejectUser(UUID) |
| block() | ACTIVE | BLOCKED | blockUser(UUID) |
| unblock() | BLOCKED | ACTIVE | unblockUser(UUID) |

Each entity method checks the current state before changing it. Every other starting state fails with InvalidAccountStatusTransitionException and leaves status untouched; repeated operations also fail. The exception has a fixed message with no database details. A future HTTP error handler can map it to the API contract's safe 409 invalid-status-transition response; no handler is implemented now. UserNotFoundException remains the error for missing IDs.

The four service methods reuse requireUser, call the corresponding entity method and saveAndFlush in a write transaction. The existing @PreUpdate callback updates updatedAt during persistence; the returned DTO therefore contains the timestamp after flushing. The transition methods themselves change only status. Role, email, password hash, profile details, ID and createdAt are preserved. No schema change or migration is needed.

getUsersByStatus(AccountStatus, Pageable) inherits UserService's read-only transaction. It requires non-null arguments, delegates to UserRepository.findByStatus and converts the result using Page.map(UserResponse::from), retaining page metadata. Supply a Pageable with explicit sorting (for example email) when stable ordering is required. API pagination limits, authenticated actor checks, self-lockout/final-administrator safeguards and audit integration remain responsibilities of the later secured administrator workflow; none are implied by this internal service implementation.

Tests added in this step:

- UserAccountStatusTests checks all 16 operation/starting-state combinations, including the four valid transitions and all twelve invalid ones. It also checks that role, email, hash and profile values remain unchanged.
- UserServiceTests now checks all four successful status operations, invalid transitions, missing IDs, protected-field preservation and status-page mapping in addition to its Step 3 tests.
- UserServiceIntegrationTests now checks each valid transition against PostgreSQL, reloads the stored user to verify status and timestamps, checks protected fields, and tests filtered multi-page results. Timestamp tests use a deliberately old database timestamp rather than sleeping. Existing tests remain in place.

```sh
# Unit tests for entity transitions and Users service; no PostgreSQL required:
(cd backend && ./mvnw -Dtest=UserAccountStatusTests,UserServiceTests test)
# Full suite after configuring a disposable TEST_DB_* PostgreSQL database:
(cd backend && ./mvnw verify)
```
